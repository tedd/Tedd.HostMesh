# Tedd.HostMesh architecture and delivery plan

Tedd.HostMesh is a private network for .NET applications and existing TCP/UDP services. Each host runs one agent. Each application can own a stable mesh IP and listen on its own ports. Agents maintain authenticated QUIC connections over UDP, deliver traffic directly when possible, and forward through authorized relays when necessary. A route change preserves every live application connection between reachable endpoints. The client keeps its stream, the service keeps its accepted socket, and both can continue reading and writing through the new route.

The first release is a userspace service overlay for Windows and Linux. A mesh IP is usable through the SDK or a configured socket forward. Ordinary OS-wide IP routing, ICMP, and transparent source addresses for arbitrary applications would require a separate virtual network interface and OS integration. The name **Tedd.HostMesh** describes the topology while leaving the transport and operating system open.

## Wire protocol

The agent uses Tedd.Quicly for authenticated neighbor links and System.Net.Quic for reliable end-to-end streams. A loopback UDP mapping at each endpoint gives the end-to-end QUIC connection a stable transport address. Relays route fragments of its encrypted packets. QUIC provides the retry buffer, acknowledgements, receive credit, duplicate suppression and final byte offsets for each stream. The operating guide covers configuration, application integration and fault simulation. [Operating guide](README.md)

## A three-host deployment

The example uses an operator-selected private prefix. Physical listener addresses and mesh service addresses belong to separate address spaces.

| Host | Physical socket or SDK endpoint | Forwarding rule |
| --- | --- | --- |
| Edge | Public TCP `203.0.113.10:443` | Accept permitted clients and forward the TLS byte stream to `10.84.2.10:443` on Web. Record the observed client IP and source port. |
| Web | Nginx, mesh `10.84.2.10:443` | Deliver to Nginx on `127.0.0.1:8443`. A dedicated PROXY-protocol listener can receive the client address before TLS. |
| Data | MySQL, mesh `10.84.3.10:3306` | Deliver authorized database flows to `127.0.0.1:3306`. Allow the application and its explicitly authorized local client forward. |
| Web | .NET application, mesh `10.84.2.11` | Accept application traffic and connect to the database. A driver that opens its own socket can use a dedicated local forward. Give that forward its own restricted identity and authenticate local callers where identity matters. |

Nginx and the application can share a host while retaining distinct identities. If Web and Data cannot peer directly, Edge can carry their traffic when authorized for transit. That permission alone grants no right to open a database connection. Node roles can be combined or deployed independently.

## Address ownership, discovery, and policy

- Give each mesh a unique ID and trust root. A signed membership manifest assigns each stable node ID its certificate identity, exclusive address prefix, seed addresses, and allowed roles. Support operator-selected IPv4 and IPv6 pools. Validate prefix overlaps and conflicting physical binds before activation.
- Reserve one address per host. Allocate application addresses persistently from its prefix, with optional static reservations. An authenticated local registration binds an application ID to its permitted addresses and listeners. Two applications can use the same port on different IPs. A second owner of the same protocol/IP/port fails registration. After restart, a returning identity reclaims its reservation.
- Advertise prefixes by node and publish service records separately. An optional mesh-scoped name resolves to the service address through the agent. Version and expire records. During a partition, each host can allocate from its existing prefix. Moving ownership across hosts requires an authorized reassignment and fencing of the previous owner. Reserve service mobility and replicated service names for a later release.
- Grant separate permissions to bind a physical listener, originate a flow, relay a flow, and deliver it to a destination. Use source CIDRs at ingress and authenticated application or gateway identities plus destination protocol/address/port at egress. Deny unmatched rules. Restrict outgoing socket targets to explicit configured destinations. Validate a configuration revision as a unit and retain the last valid revision on reload.

## Transport and forwarding

Use the raw MsQuic carrier in Tedd.Quicly behind a small mesh transport adapter. Its public `ITransport` exposes bidirectional streams, datagrams, receive credit, send completions, and connection statistics. The higher-level `ReliableOrdered` game channel has a persistent stream per declared channel. A mesh with dynamic sockets needs independent flow control per connection. Pin a tested Quicly package version after exercising the carrier on both platforms. [Quicly transport contract](https://github.com/tedd/Tedd.Quicly/blob/2c506b0eaff0a308fd2d0a03c9362ba6146fb0be/src/Tedd.Quicly.Core/Transport/ITransport.cs) · [QUIC streams and flow control](https://www.rfc-editor.org/rfc/rfc9000.html#section-2)

| Traffic | Wire behavior | Application contract |
| --- | --- | --- |
| Routing and admission | Priority heartbeats and periodically refreshed, signed link-state advertisements on authenticated neighbor datagrams | Version negotiation, membership, route advertisements, withdrawals, keepalives and diagnostics remain responsive under data load. |
| TCP or SDK stream | Encapsulate end-to-end QUIC packets in neighbor datagrams. Each relay forwards them using its current next hop. | One ordered, duplex byte stream across route changes, with independent half-close and backpressure. A successful open means the destination has accepted the SDK connection or opened the target socket. |
| Native UDP | QUIC DATAGRAM frames carry the mesh destination and a stable association ID. Replies route to the originating mesh endpoint. | Preserve datagram boundaries, the return mapping and the local UDP socket across reroutes. In-flight datagrams can be lost or reordered. Expire idle associations. Account for the current route’s payload limit, report oversized SDK sends and count drops at socket bridges. |
| Reliable messages | Encode complete length-prefixed messages over a reliable mesh flow. Negotiate this mode at open. | Preserve message boundaries and order across reroutes. Deliver each complete message once to the same live receiver. Applications that need proof of processing supply an application acknowledgement. |

Use a mesh-specific ALPN and versioned frames with bounded lengths. Each routed record identifies the source and destination nodes, traffic class, and remaining hop limit. Reassembly metadata identifies the endpoint tunnel and packet. Agents authorize transit, decrement the hop limit and consult their local forwarding table. Link-local QUIC streams and cached policy decisions are disposable. A relay joining the path can forward an existing flow using the record header and its current routing table. Each endpoint authenticates the other agent and applies application policy. Loss of a relay and its queued records is recoverable from the endpoints’ unacknowledged data. Pool buffers and reserve processing time for control traffic and acknowledgements. [QUIC datagram size and delivery semantics](https://www.rfc-editor.org/rfc/rfc9221.html#section-5)

## Connection continuity

Only the two endpoint agents own the application connection. For a socket forward, each retains its original local socket. For an SDK connection, each retains its registration and stream handle. Route selection can change independently in each direction. A routing-table update can therefore move the next record to a different neighbor while older records are still in flight.

- **Open once.** Identify a flow by the endpoint node identities and agent incarnations plus a unique flow ID. Bind the application identities, addresses and delivery mode at admission. Deduplicate repeated `OPEN` requests, including retries while a target connect is pending. A lost `OPEN_ACK` returns the original result on retry. Reject records for an unknown or closed flow. Retain terminal state through the retry horizon and fence packets from expired incarnations.
- **Acknowledge at the endpoints.** Each direction has independent byte offsets, a cumulative acknowledgement and an advertised receive window. Authenticate endpoint control records against the admitted flow, and reject acknowledgements beyond the highest sent offset. The sender retains the unacknowledged suffix. Advance the acknowledgement only after the receiving endpoint owns the contiguous bytes in its bounded delivery queue or has written them to the original socket. Drain that queue in order. A relay acknowledgement or QUIC send completion cannot release the endpoint retry buffer.
- **Repair in flight.** Send new data and acknowledgements using the current next hop. On a route-change signal or a stalled end-to-end acknowledgement, retransmit the outstanding range on the current route within the peer’s window. Pace retries with RTT-based timers and backoff. The receiver trims overlapping ranges, emits each byte once, and returns its current acknowledgement when duplicates arrive. This also handles lost acknowledgements, delayed records from the old path and switches initiated by a transit node.
- **Bound memory and waiting.** Enforce per-direction, per-application and per-agent byte limits, including out-of-order receive data. When the window fills, pause reads from the local socket or await SDK writes. Reserve capacity for acknowledgements, window updates and probes so a lost credit update can recover during backpressure. A temporary partition can stall a flow until a permitted path returns. Configure the maximum outage duration separately from connect and application deadlines.
- **Close at the correct boundary.** Carry each half-close as an acknowledged final byte offset. Deliver EOF once all preceding bytes have reached the local consumer, and keep the opposite direction usable. An adjacent QUIC reset signals a forwarding failure and triggers repair. A flow terminates on an authenticated endpoint abort, loss of endpoint state or its original socket, authorization revocation, or expiry of the configured outage deadline. Address continuity and origin metadata last for the lifetime of the flow.

## Route selection and repair

1. **Form a sparse graph.** Start with several configured seed endpoints and outbound connections to at least two reachable relays where redundancy is required. Reuse a bidirectional adjacency for flows initiated from either side. Resolve simultaneous dials deterministically. Discover permitted direct neighbors and cap their number. An outbound-only node can serve inbound flows over a connection it initiated. If neither side can accept UDP, use a reachable relay. Networks that block all outbound UDP require a separate carrier.
2. **Distribute directed link state.** Each node advertises its own neighbor reachability, administrative cost, allowed transit classes, capacity cap, smoothed RTT, loss and estimated goodput. Authenticate the origin, use a persistent generation and increasing sequence, expire stale state, and reconcile snapshots after reconnection. Require recent confirmation at both ends before using an adjacency. Coalesce updates and refresh periodically.
3. **Apply policy before scoring.** Remove forbidden relays, unavailable links, paths over the hop limit and paths incompatible with the requested delivery mode. For interactive traffic, minimize cumulative delay with an administrative penalty. For bulk traffic, maximize the lowest usable link capacity on the path, then minimize delay. Cap measurements by configured capacity. An idle link has unknown capacity. Use a conservative configured estimate until traffic or a rate-limited probe supplies a sample. Use stable node IDs to break ties and prefer direct paths at comparable cost.
4. **Update forwarding tables for live traffic.** Smooth metrics, require a sustained improvement before changing preference, and retain a warm alternate through a different relay where available. A hard link failure invalidates its next hop immediately. Publish the replacement table atomically for new and established flows. Use the destination, applicable transit policy and traffic class for lookups, with a stable flow hash for equal-cost choices. Bound transient loops with a per-record hop limit. Reconnect adjacencies with jittered backoff. Peers can forward on valid cached state when seeds are offline.

## .NET API and client address provenance

The local SDK authenticates each listener, connection, and datagram binding at the application's configured Unix-domain socket on Windows and Linux. Map OS credentials to application identity. Applications sharing a service account need distinct credentials or service identities to obtain separate grants. The agent owns peer connections and routing independently of the application lifecycle.

| Proposed SDK operation | Result |
| --- | --- |
| `RegisterAsync(appId)` | Assigned mesh addresses, permissions and session lifetime. |
| `ListenAsync(localMeshEndpoint)` / `AcceptAsync()` | A listener and accepted duplex connections. Each exposes a .NET `Stream`, `CompleteWritesAsync`, local endpoint and verified peer context. |
| `ConnectAsync(destination, localAddress, cancellationToken)` | An outbound flow sourced from an address owned by the caller. Report refusal, denial, initial route unavailability and connect timeout at open. The returned stream continues across route changes and exposes terminal failures if recovery expires or an endpoint closes. |
| `BindDatagramAsync(localMeshEndpoint, deliveryMode)` | A message socket with `SendToAsync` and `ReceiveFromAsync`, origin metadata per association, cancellation and path payload limits. |

Expose the initiating mesh endpoint and principal, the external client endpoint observed by an authorized ingress when one exists, and the ID of the ingress node that attests to it. For an internal caller, the effective client IP is its assigned mesh address. For an external caller, it is the address the trusted ingress observed, which can be a NAT or upstream proxy. For streams, carry the ingress assertion inside the mutually authenticated end-to-end QUIC session and bind it to the opening stream. For native datagrams, verify the node signature, authenticated source ownership, timestamp and ingress grant. Ignore address claims from ordinary clients. Each new application connection starts a new origin context.

For ASP.NET Core, provide an optional Kestrel transport adapter exposing the effective remote endpoint and a feature containing provenance. For outbound HTTP over TCP, adapt the mesh stream to `SocketsHttpHandler.ConnectCallback`. A raw socket service normally sees its adjacent bridge. Supply PROXY protocol v2 only to dedicated, compatible listeners such as a configured Nginx endpoint. If Nginx creates a new HTTP request, use an explicitly trusted proxy chain for the HTTP client address. [NGINX PROXY protocol](https://docs.nginx.com/nginx/admin-guide/load-balancer/using-proxy-protocol/) · [.NET HTTP connection callback](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.connectcallback)

## Trust and operations

Assume one administrative trust domain for the first release. Authenticate both nodes before routing or opening traffic. Verify mutual certificate support on the selected Quicly carrier as an implementation gate. If needed, extend the binding for mTLS before deployment. Bind node identity, mesh membership and roles to the authenticated session. Rotate certificates with an overlap window, persist revocation state, and close affected sessions on revocation. A partitioned node can enforce only the last revocation state it received. Credential and policy expiry bound that exposure.

Relays terminate the neighbor QUIC hop. Reliable application streams retain end-to-end QUIC encryption across every relay. Native UDP payloads are signed end to end and encrypted on each neighbor link, and an authorized relay can read them. Applications can carry their own encrypted UDP protocol when payload confidentiality across relays is required.

Expose peer status, reachability, selected path and reason, alternate path, last topology revision, route age, RTT, observed goodput and UDP drops. For reliable flows, report unacknowledged bytes, retransmitted bytes, credit stalls, time to resume useful traffic and the cause of terminal resets. Provide a route-explanation command that identifies the specific policy or link excluding a path. Audit registrations, ingress assertions and policy changes without recording payloads.

## Delivery sequence and acceptance

| Milestone | Deliverable | Acceptance gate |
| --- | --- | --- |
| 1. Two-host reliable flow | Prove mutual authentication and both traffic modes with Quicly. Implement endpoint flow IDs, offsets, acknowledgements, credit and half-close. | On Windows and Linux, replace the entire peer QUIC connection mid-transfer. Verify a single application accept, unchanged endpoint sockets and byte-for-byte delivery in both directions. Lose an open acknowledgement and a final acknowledgement. A retry causes neither a second accept nor premature EOF. |
| 2. Applications and bridges | Agent, persistent addresses, local SDK registration, socket forwards, policy, client provenance and reliable messages. | Two applications bind the same port on distinct IPs. Verify TCP half-close, stable UDP reply mapping, datagram size limits, denied binds, source attribution and delivery through an unmodified TCP service. Verify message boundaries across a reroute. |
| 3. Multi-hop routing | Authenticated link state, policy-aware forwarding tables, warm alternates and route explanations. | Run a full-duplex numbered stream through a four-node diamond. First change route preference under load, then kill the active relay with data and acknowledgements in flight. Delay old-path frames and drop acknowledgements in one direction. Require one client connect and one service accept for the entire test, unchanged addresses, identical ordered bytes, and half-close exactly once in each direction. Repeat with different forward and return paths. |
| 4. Performance and operations | Capacity estimates, stable route preference, bounded buffers, reload, certificate rotation, revocation and version negotiation. | Partition all paths until the retry buffer fills. Verify backpressure, bounded memory, and recovery on the same socket when a route returns within the deadline. Separately verify a terminal error after deadline expiry or endpoint restart. Compare CPU, goodput and p99 latency with direct sockets. With a warm alternate and a writable receiver, the proposed lab target is for the existing stream to acknowledge new bytes within 5 seconds of a black-holed link. |
| 5. Extensions selected by deployment need | NAT hole punching, service mobility, an OS virtual adapter, or an alternate carrier. | Give each feature a separate compatibility and fault test. |

The reusable boundary is narrow. Adapt TcpTunnel's CIDR matching, socket binding, stream lifecycle, telemetry and tests while applying mesh policy defaults. Borrow TDFS's peer-pool ownership, jittered reconnect and deterministic fault scenarios. Use Quicly's simulated carrier for repeatable network failures and its real carrier for interoperability and measurements. TDFS consensus and storage can evolve independently of the mesh. Size retry windows against target throughput and acknowledgement latency, cap aggregate memory, and set the outage deadline from the deployment’s recovery objective.
